## Что решаем

Бесплатный тариф Cloudflare даёт небольшому сайту DNS-серверы, HTTP-прокси, CDN и базовую защиту. DNS-серверы здесь отвечают за адрес домена, а прокси принимает веб-запрос раньше сайта. Там же есть технические данные о запросах, Access для закрытых экранов и Tunnel для публикации приложения без платного Access.

Польза в одном месте, где запрос виден и управляется до сайта. Риск там же: один переключатель может остановить поискового или AI-робота ещё до вашего журнала запросов.

Я оставляю этот слой только там, где могу назвать его задачу и проверку результата. Само имя Cloudflare позиции не поднимает, а платформе с теми же функциями новый слой может быть не нужен.

Граница тут практическая. Если публичный запрос должен дойти до сайта, я обязан знать, какая настройка Cloudflare способна его остановить, где виден этот отказ и как повторить проверку без активного входа в браузере.

Слой должен объясняться. Если я не могу одной фразой назвать задачу конкретного переключателя, то не включаю его до появления такой задачи, потому что бесплатная возможность всё равно добавляет ещё одно место для скрытой поломки.

## Шаги

### Что меняется, когда Cloudflare становится DNS-провайдером

Cloudflare может отвечать за DNS без переноса домена от регистратора. У регистратора меняются серверы имён, а записями вы дальше управляете в Cloudflare.

Серая запись работает только как DNS: Cloudflare отвечает на запрос имени, а посетитель подключается к сайту напрямую. Оранжевая запись работает через прокси, поэтому веб-трафик проходит через Cloudflare и попадает под защиту, кэш и технические отчёты.

Разница важная: функции прокси не действуют на серую запись. Я сначала проверяю цвет облака и только потом ищу ошибку в кэше или правиле безопасности.

### Что экономят бесплатные прокси и кэш

Бесплатный тариф для сайтов включает CDN, TLS и защиту от DDoS. Для статического сайта первая польза проще: картинки, CSS и JavaScript можно отдать из кэша Cloudflare, и повторные запросы до сайта не дойдут.

HTML по умолчанию не кэшируется. Я не считаю главную закэшированной только потому, что включено оранжевое облако: смотрю заголовки ответа и правила кэша.

У кэша есть обратная сторона — ещё одна старая копия. После выкладки проверьте изменённый файл снаружи своего браузера и только потом ищите ошибку в сборке.

### Какая аналитика работает без счётчика в браузере

Zone Analytics читает запросы, которые увидела сеть Cloudflare. На бесплатном тарифе там есть HTTP-трафик, DNS и события безопасности, поэтому видно, пришёл ли запрос и остановило ли его правило до сайта.

Это технические данные. Они не скажут, получил ли человек результат, заплатил ли и вернулся ли; эти факты продукт пишет сам, как на странице [что должна нести строка события](/ru/analytics/product-metrics/).

Cloudflare Web Analytics — другой продукт с кодом-счётчиком в браузере. Atlas этот код и внешние скрипты аналитики не добавляет. Бесплатная функция не даёт причины менять обещание о приватности.

### Когда нужны Access и Tunnel

Access ставит проверку личности перед закрытым приложением. Бесплатный тариф рассчитан на команды меньше пятидесяти человек, чего хватает для ранней внутренней панели или экрана администратора.

Перед публичной документацией Access ставить нельзя. Робот не войдёт через вашу форму, поэтому страница пропадёт из поиска, хотя у вас будет открываться нормально.

Tunnel публикует приложение через исходящее соединение и не требует платного Access. Инструменты решают разные задачи: Tunnel проводит соединение, Access решает, кого пропустить. Видимость в поиске сами по себе они не улучшают.

### Какие бесплатные правила для ботов помогают, а какие прячут сайт

На бесплатном тарифе есть Bot Fight Mode и управление доступом AI-роботов. Текущие политики разделяют Search, Agent и Training, поэтому им не обязательно давать один ответ.

Публичному справочнику, который хочет попадать в ответы, надо разрешить Search и Agent. Training решается отдельно. Старый общий переключатель *Block AI bots* для этой цели слишком широкий: он может остановить нужного вам агента.

Ошибка тут дорогая. Владелец с активным входом продолжает видеть нормальную страницу, пока анонимный робот получает отказ, поэтому без внешней проверки можно неделями чинить текст, который поиск ни разу не прочитал.

После включения правила для роботов я не верю снимку панели: делаю внешний запрос без сохранённого входа, читаю код и тело ответа и только тогда считаю публичный путь открытым для поиска, потому что собственная сессия легко скрывает форму входа или проверку браузера.

Bot Fight Mode действует на весь домен, а на бесплатном тарифе для него нельзя сделать исключение. Я включаю его только после внешней проверки настоящих роботов, мониторинга и обратных вызовов продукта.

### Зачем вообще брать Cloudflare

Cloudflare полезен мне там, где домен, прокси, кэш и правила на границе сети должны жить отдельно от платформы приложения. Тогда при смене платформы меняется DNS-запись, а публичные адреса и слой управления остаются.

Если платформа уже решает те же задачи и добавлять правило не нужно, я пропускаю Cloudflare. Ещё одна панель сама по себе надёжности не даёт: в ней просто появляется ещё одна настройка, которая может разъехаться.

## Что не сработало

- **Включить все бесплатные переключатели.** Правила для роботов и Access не безобидные подарки. Оба могут отдать роботу проверку, форму входа или отказ вместо здоровой публичной страницы.
- **Считать, что оранжевое облако кэширует HTML.** Статические файлы приходили из кэша, а документ каждый раз забирался с сайта. Настройка работала правильно, ошибался я.
- **Искать блокировку только в журнале сайта.** Отказ в сети Cloudflare туда не дошёл. Он остался в событиях безопасности.
- **Поставить Access перед публичной документацией.** В моём браузере с активным входом всё выглядело хорошо, а анонимный запрос видел форму. Публичный справочник должен оставаться публичным.
- **Добавить счётчик только потому, что он бесплатный.** Он не отвечал ни на один продуктовый вопрос и менял обещание о приватности. В Atlas я его не ставил.
- **Считать Tunnel настройкой SEO.** Он меняет путь до приложения. Робот всё равно читает публичный ответ, канонический адрес, текст и ссылки.

## Проверить

- Спросите DNS, какие серверы имён отвечают за домен. Должны вернуться те, которые вы осознанно поставили у регистратора.

  ```bash
  dig +short NS example.com
  ```
- Дважды запросите статический файл и прочитайте `CF-Cache-Status`, `Cache-Control` и код ответа. Значение `HIT` доказывает только кэш этого файла и ничего не говорит про соседний HTML.

  ```bash
  curl -sI https://example.com/assets/app.css
  ```
- Откройте публичную страницу в приватном окне. Контент должен прийти без формы Access и без проверки браузера.
- В **Analytics** найдите тот же путь в HTTP Traffic и Security Events. Запрос, остановленный там, может не попасть в лог приложения.
- Прочитайте живой `robots.txt`, потом откройте политики Search, Agent и Training в разделе **Security**. Файл и панель должны выражать одно осознанное решение.
- Проверьте одного поискового робота и одного агента, который приходит по просьбе пользователя, из внешней сети. Для попадания в AI-ответы оба должны получать обычный успешный ответ.
