## Что решаем

Сайт в проде уже недели, а поиск по нему не отдаёт ничего. Не слабая позиция — вообще ни одного результата.

Индексация ломается сверху вниз. Страницу сначала надо получить, потом обойти, потом проиндексировать, и только потом она может ранжироваться.

Переписанный `title` на странице с `noindex` не меняет ничего. Поэтому проверки ниже идут по порядку, и останавливаться надо на первой упавшей: на заблокированной странице всё, что ниже, измерить нельзя.

## Шаги

### Получает ли crawler хоть какой-то текст

Первое, что я проверяю, — что отдаёт сервер до всякого JavaScript. Забираете страницу и ищете в ответе предложение, которое видно на ней глазами:

```
curl -sL https://example.com/page | grep -i "фраза, которую видно на странице"
```

Если grep молчит, а в браузере текст есть, значит его дорисовывает клиент. Клиентское приложение отдаёт почти пустой `<body>`, и crawler получает страницу, в которой индексировать нечего. Лечится это серверным рендерингом или пререндером на сборке, а не тегами.

### Что на самом деле написано в вашем robots.txt

Файл надо забрать с боевого домена и прочитать целиком, а не те строки, которые вы туда писали сами:

```
curl -s https://example.com/robots.txt
```

Классика — `Disallow: /`, приехавший из конфига стенда вместе с деплоем. Второй случай тише: Google перестаёт читать файл после 500 кибибайт, так что сгенерированный robots может молча обрезаться где-то посередине, и всё, что было ниже, для него не существует.

### Не просите ли вы поиск выбросить страницу

`noindex` живёт в двух местах, и в одном из них его не видно глазами. Мета-тег лежит в HTML, а второй — это заголовок ответа `X-Robots-Tag`, который в исходном коде страницы не показывается вообще:

```
curl -sI https://example.com/page | grep -i x-robots-tag
```

`curl -sI` шлёт HEAD-запрос и печатает одни заголовки. В браузере то же самое лежит во вкладке Network, в запросе документа, в секции Response Headers.

Ставить этот заголовок может фреймворк, веб-сервер или CDN — каждый из них отдельный файл, который придётся открыть. Есть ещё форма для конкретного агента, `X-Robots-Tag: googlebot: noindex`, и она выглядит как обычная строка конфигурации.

Страницу с `noindex` при этом честно забирают и разбирают, а потом намеренно выбрасывают.

### Сколько у страницы адресов и куда она показывает

Каждая страница должна указывать canonical на себя или на реальный оригинал:

```
curl -sL https://example.com/page | grep -i 'rel="canonical"'
```

Шаблон, который зашивает главную как canonical на всех страницах разом, буквально просит поиск выкинуть весь остальной сайт.

Дальше — сколько форм адреса отвечают одной и той же страницей. Слеш в конце, `www`, `http`, `index.html` и параметры трекинга должны редиректиться к одной форме:

```
for u in http://example.com/page https://www.example.com/page https://example.com/page/ https://example.com/page/index.html; do
  curl -o /dev/null -sw "%{http_code} %{redirect_url}\n" "$u"
done
```

Иначе сигнал делится между дублями, а sitemap начинает спорить с тегом canonical, и поиск разбирается с этим спором сам, без вас.

### Живой ли sitemap, а не просто лежит ли он

Проверять надо не наличие файла, а то, что каждый URL в нём отвечает 200, записан абсолютно и в канонической форме:

```
curl -s https://example.com/sitemap.xml | grep -o '<loc>[^<]*' | cut -c6- |
  while read -r url; do curl -o /dev/null -sw "%{http_code} $url\n" "$url"; done
```

Протокол ограничивает один файл 50 000 URL и 50 МБ без сжатия — дальше файл надо разбить и добавить sitemap index. Карта, набитая редиректами и 404, обесценивает сама себя: её перестают читать как источник правды о сайте.

### Видно ли сайт снаружи вашей сети

Последняя проверка не запускается с вашей машины. Резолвить домен надо с другого адреса и запрашивать страницу без кук:

```
ssh other-box 'curl -sI https://example.com/page'
```

Access-контроль, basic auth и bot-правила на edge отдают в ответ логин-форму или 403, и в `robots.txt` ничего этого не видно.

У правила на edge есть имя и экран. В Cloudflare это **Configure AI bot policies** на странице **Security Settings** зоны, на всех тарифах. Подходящим агентам оно отвечает 403 из сети Cloudflare, до того как запрос дойдёт до вашего сервера.

Поэтому в логе сервера отказа тоже нет — он виден только в **Analytics** → **Events** у Cloudflare. Весь механизм разобран здесь: [AI-crawler и llms.txt](/ru/geo/llms-txt-and-crawlers/).

## Что не сработало

- **Ждать, пока индекс догонит**. Crawler действительно возвращается, читает то же правило и уходит. Терпение не правит заголовок.
- **Отправить один URL заново в инструменте проверки**. Перезапрос идёт по тому же `robots.txt`, с тем же заголовком и тем же пустым телом. Вердикт возвращается тот же, дневная квота потрачена.
- **Считать доказательством доступа отчёт стороннего crawler**. Он показывает, что смог забрать бот с его собственного адреса. Решил ли поиск оставить страницу — вопрос другой.
- **Проверять только со своего ноутбука**. Залогиненная сессия, прогретый service worker и домашняя сеть, которой edge уже доверяет, прячут поломку целиком. Edge — это CDN перед вашим origin: Cloudflare, Fastly, облачный балансировщик. Часть запросов он отвечает сам, и до вашего сервера и его лога они не доходят.
- **Править `robots.txt`, когда блок жил на edge**. Правила bot-protection и WAF в этом файле не видны, а сам файл был чистым всё это время. Искать надо **Configure AI bot policies** под **Security Settings** у Cloudflare и любое custom-правило WAF рядом. Это самый частый спрятанный блокер, который мне попадается.
- **Сначала переписать `title` и описания**. На странице, которой нет в индексе, работа с текстом не даёт ничего измеримого.

## Проверить

Запустить скилл `seo-audit` из раздела [Tools](/ru/tools/). Он проходит этот же порядок и собирает ответы в один отчёт — быстрее, чем проверять всё это руками.

Потом подтвердить то, что отчёт подделать не может:

- `curl -sI` на странице отдаёт 200 и не несёт `X-Robots-Tag`.
- `curl -sL` на том же URL содержит предложение, которое видно на странице.
- URL Inspection в Search Console говорит, что URL есть в Google.
- В **Analytics** → **Events** у Cloudflare, с фильтром по действию Block, для ваших URL пусто. Заблокированный crawler виден там и больше нигде.

Грубая прикидка того, сколько страниц вообще дошло до индекса, делается прямо в поисковой строке:

```
site:example.com
```

Формулировки в Search Console читать буквально. «Discovered — currently not indexed» значит, что URL известен и не был забран. «Crawled — currently not indexed» — забран и признан не стоящим хранения. Это два разных бага с двумя разными починками.

Как только в индекс попала первая страница, отдавайте остальные: [отдать и проверить](/ru/indexing/submit-and-verify/).
